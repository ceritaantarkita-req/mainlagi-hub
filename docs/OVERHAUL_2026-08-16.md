## 1. Struktur Git — kenapa dan bagaimana

Kamu minta: kerjaan sekarang masuk ke `main`, dan `main` yang lama dipindahkan ke branch.

### Kondisi sebelumnya

```
origin/main                              ← tertinggal 63 commit, terakhir 5 Agu 2026
feature/mainlagitv-motion-engine-v3      ← semua kerja V3 ada di sini (HEAD)
```

Ditambah **46 file yang terlihat "modified" padahal bukan** — diffnya 14.506 baris tambah
dan 14.506 baris hapus, angka yang persis sama. Itu murni konversi CRLF↔LF dari Windows,
bukan perubahan kode. Penyebabnya `.gitattributes` hilang dari tree.

### Kondisi yang dituju

```
archive/main-legacy-20260816   ← isi main yang lama, diarsipkan utuh, tidak hilang
main                           ← V3 + semua perbaikan hari ini
```

### Cara menjalankannya

Aku **tidak bisa** menjalankan perintah git di folder kamu: git gagal membuat dan menghapus
file lock lewat jembatan folder ini (`Operation not permitted` pada `.git/index.lock` dan
`.git/packed-refs.lock`). Jadi file kode sudah ditulis ke disk kamu, tapi commitnya harus
kamu jalankan sendiri.

Skrip lengkapnya ada di **[`GIT_RESTRUCTURE_20260816.ps1`](../GIT_RESTRUCTURE_20260816.ps1)**
(PowerShell, tinggal klik kanan → Run with PowerShell, atau jalankan dari terminal).

Ringkasan yang dilakukan skrip itu:

1. Hapus file lock yang tertinggal (`.git/index.lock`, `.git/packed-refs.lock`)
2. Pulihkan `.gitattributes` lalu `git add --renormalize .` → 46 file palsu itu hilang
3. `git branch archive/main-legacy-20260816 origin/main` → **main lama diselamatkan dulu**
4. `git checkout main && git reset --hard feature/mainlagitv-motion-engine-v3`
5. Commit semua perubahan hari ini ke `main`
6. Push `archive/main-legacy-20260816` dulu, baru `main --force-with-lease`

**Urutannya penting**: arsip dibuat dan di-push *sebelum* `main` ditimpa. Kalau langkah
push arsip gagal, skrip berhenti dan tidak menyentuh `main` sama sekali.

### Satu hal yang perlu kamu cek sendiri

Tidak ada workflow deploy di dalam repo — `.github/workflows/` cuma berisi `ci.yml`.
Artinya `mainlagi.inmydraft.com` dideploy dari luar repo (Vercel/Netlify/Cloudflare).
**Pastikan branch yang di-hook adalah `main`.** Kalau selama ini yang di-hook `main`,
maka semua kerja V3 memang belum pernah tayang — dan setelah restrukturisasi ini, sekali
push semuanya langsung naik.

## 2. Skeleton tracking

### 2.1 Tangan kedua tidak lagi dibuang

`src/lib/vision/useVisionRuntime.ts`

Kode lama meminta model mendeteksi 2–4 tangan, lalu membuangnya:

```ts
if (!player || hands.some((hand) => hand.player === player)) continue;
```

Karena `assignHandToPlayer` mengembalikan `"A"` untuk semua tangan saat 1 pemain, tangan
kedua selalu kena `continue`. Satu pemain **selamanya** cuma punya satu tangan di layar.
Itulah kesan "skeletonnya kurang".

Sekarang: dua tangan per pemain, masing-masing punya slot filter sendiri
(`HandSlotState`), sehingga smoothing tidak lompat antar tangan. Yang tetap satu tangan
hanyalah **pena** — dan pemilihannya lengket (`PrimaryHandSelector`): tangan yang sedang
mencubit memegang pena sampai berhenti mencubit selama 600 ms, jadi tangan lain yang
kebetulan masuk frame tidak mencuri stroke di tengah huruf.

### 2.2 Pose sekarang 33 titik

`src/components/VisionOverlay.tsx`

Dari 12 garis menjadi 35 koneksi: wajah, lengan, **telapak tangan**, torso, kaki, dan
**telapak kaki**. Sebelumnya tubuh tampil tanpa kepala dan tanpa kaki.

### 2.3 Jari digambar per jari

Setiap jari punya rantai dan warnanya sendiri (jempol kuning, telunjuk hijau, dan
seterusnya), ujung jari radiusnya lebih besar dari ruas, buku jari di antaranya. Ukuran
garis dan titik sekarang **skala terhadap ukuran kanvas** (`strokeScale`) — dulu radius
tetap 3px, jadi di HP 21 titik saling menempel jadi gumpalan.

Ujung telunjuk tangan pena diberi cincin, dan cincinnya berubah hijau saat mencubit —
supaya anak lihat persis titik mana yang diikuti sistem.

### 2.4 Overlay sekarang lurus dengan video

Overlay lama memetakan koordinat 0–1 langsung ke kanvas penuh, jadi skeleton bergeser dan
meregang. Sekarang semua konsumen koordinat lewat satu transform yang sama.

## 3. Face mesh — empat kegunaan, bukan hiasan

`src/lib/vision/face-analysis.ts` — modul baru.

Kamu memilih keempat kegunaan, dan keempatnya diimplementasikan:

| Kegunaan | Implementasi |
|---|---|

tidak memakan budget FPS.

mengunduhnya; kalau gagal, runtime otomatis pakai URL resmi Google.

## 4. Akurasi tulis — ini bagian terpentingnya

### 4.1 Kenapa 6 dan 9 tertukar

Kode lama, `src/lib/engine/digit.ts`:

```ts
return Math.min(
  pathDistance(input, target),
  pathDistance(mirrored, target),            // menerima tulisan dicermin
  pathDistance(input, [...target].reverse()) // menerima tulisan dibalik arah
);
```

**6 dan 9 adalah rotasi 180° satu sama lain.** Setelah posisi dinormalisasi ke titik
berat, lalu cermin dan pembalikan urutan diterima, ruang perbedaan antara keduanya nyaris
hilang. Ini bukan soal tuning threshold — secara matematis keduanya jadi bentuk yang sama.

Hal yang sama membunuh huruf Arab: د vs ر dan ذ vs ز dibedakan justru oleh arah, dan
tulisan Arab itu RTL.

**Mirror matching dihapus total.** Ada guard di `scripts/audit-source.mjs` supaya tidak
bisa kembali diam-diam — CI akan gagal kalau `mirrorPath` muncul lagi di recognizer.

### 4.2 Recognizer baru

`src/lib/engine/pointcloud.ts` (baru) — recognizer **$P point-cloud**
(Vatavu, Anthony & Wobbrock, ICMI 2012).

Kenapa $P:

- **Pen-up dihormati.** Glyph diperlakukan sebagai awan titik tak berurutan, jadi angkat
  jari tidak lagi membuat garis hantu. Kode lama menyambung semua stroke ujung-ke-ujung
  (`strokes.flatMap(...)`), yang merusak angka 4 dan 5 secara total.
- **Urutan stroke tidak masalah.** Anak boleh menulis batang "4" duluan atau belakangan.
- **Kecepatan tidak masalah.** Titik dialokasikan proporsional terhadap panjang stroke,
  jadi titik kecil yang digambar pelan tidak mendominasi awan.

Dua normalisasi dijalankan dan yang terbaik dipakai: `uniform` (mempertahankan rasio,
inilah yang membedakan 1 dari 0) dan `square` (bebas rasio, karena tulisan tangan sering
gepeng atau memanjang). `uniform` diberi bobot sedikit lebih tinggi supaya menang saat
seri.

### 4.3 Fitur struktural sebagai pemutus

`src/lib/engine/features.ts` (baru)

Jarak bentuk saja tidak cukup. Yang benar-benar membedakan 6 dari 9 adalah **di mana
lingkarannya berada** — bawah untuk 6, atas untuk 9. Itu fakta struktural, bukan jarak.

Deteksi loop tidak hanya mencari persilangan tepat, tapi juga tempat di mana lintasan
kembali mendekati dirinya sendiri (dalam 9% diagonal) setelah menempuh jarak berarti —
karena tulisan tangan anak (dan template ideal sekalipun) sering tidak benar-benar
bersilangan.

Terukur pada template:

```
6  → loop di 0.63  (paruh bawah)
9  → loop di 0.37  (paruh atas)
0  → loop di 0.42, satu lingkaran tertutup
```

Fitur lain yang dipakai: rasio aspek (untuk 1), jumlah persilangan (untuk 8), titik awal
dan akhir, arah awal, total putaran, dan kompleksitas.

### 4.4 Angka lebih dari satu digit — "10", "69"

`src/lib/engine/multi-digit.ts` (baru)

Dulu "10" harus ditulis begini: cubit → tulis "1" → buka telapak, **tahan 700 ms** →
cubit → tulis "0" → buka telapak, tahan 700 ms. Untuk anak 5 tahun itu praktis mustahil.

Sekarang seluruh angka ditulis sekali jalan. Segmentasi dua tahap:

1. Kelompokkan stroke jadi kolom berdasarkan celah horizontal — kasus normal.
2. Kalau satu stroke jauh terlalu lebar untuk satu digit (anak menyambung "6" dan "9"
   tanpa angkat jari), potong di lembah terdalam profil kepadatan horizontalnya.

Karena game tahu jawabannya berapa digit, segmentasi dipaksa menghasilkan tepat sejumlah
itu — petunjuk yang sah dan sangat kuat.

### 4.5 Pena: dari relatif ke absolut

`src/lib/interaction/pen-mapper.ts` (baru, menggantikan `relative-hand-mapper.ts`)

Mapper lama bekerja seperti trackpad: `cursor += Δtangan × gain`. Itu **mengintegrasikan**
posisi — setiap sisa jitter yang melewati dead zone ikut tertambah dan **tidak pernah
dikoreksi**. Random walk klasik. Efek nyatanya: garis lurus melengkung, lingkaran tidak
menutup, dan pena melayang sampai user menekan "Tengah".

Mapping relatif itu tepat untuk memilih menu, **salah** untuk menulis, karena saat menulis
bentuk lintasannya *adalah* jawabannya.

Sekarang mapping absolut terhadap kotak jangkauan yang adaptif: kotaknya mulai dari area
nyaman di sekitar posisi tangan pertama, melebar saat pemain menjangkau lebih jauh, dan
menyusut sangat lambat. **Kotaknya dibekukan saat pena turun** (`lock()`), supaya huruf
tidak diskalakan ulang di tengah penulisan.

Diuji: 400 frame jitter berkelanjutan menghasilkan drift < 0.03 — mapper lama akan
melayang jauh.

### 4.6 Awal stroke tidak lagi terpotong

Pengenalan cubitan butuh satu-dua frame untuk yakin, jadi ~100–150 ms pertama setiap huruf
hilang — justru bagian yang membedakan 6 dari 0. Sekarang `MotionPad` menyimpan ring
buffer pra-cubit dan **menyambungkannya kembali** ke stroke, jadi pena boleh mulai
optimistis. Ambang cubitan juga pakai histeresis (masuk di 0.40, keluar di 0.56) supaya
tidak berkedip di batas dan memecah stroke jadi dua.

### 4.7 `hand.confidence` yang ternyata bukan confidence

```ts
const confidence = handResult?.handedness[index]?.[0]?.score ?? analyzed.confidence;
```

Itu skor **handedness** (kiri/kanan), yang hampir selalu > 0.95. Nilai confidence gesture
yang sebenarnya dibuang. Akibatnya semua cek `hand.confidence >= MIN_HAND_CONFIDENCE`
tidak berfungsi sama sekali. Sekarang ada field terpisah `gestureConfidence`.

### 4.8 Hasil terukur

Diuji dengan tulisan sintetis + jitter, sebagai test suite permanen:

```
Akurasi klasifikasi digit  : 96% (10 angka × 2–3 varian × 3 tingkat jitter)
6 vs 9                     : 0 kesalahan, jarak terbaik ~0.004 vs pesaing ~0.030
Verifikasi jawaban benar   : 97% diterima
False accept jawaban salah : 0.9%
Multi-digit 10/69/100/12/45: 10/10 diterima, termasuk spasi rapat
Jawaban salah (69 vs 96)   : semua ditolak
```

## 5. Huruf Hijaiyah

`src/lib/engine/hijaiyah.ts` — ditulis ulang.

Empat masalah struktural yang diperbaiki:

1. **Stroke terpanjang dianggap badan huruf.** Anak yang menulis titik pelan-pelan
   menghasilkan lebih banyak titik data di sana, dan huruf dinilai terhadap sebuah titik.
   → Sekarang pemisahan berdasarkan **ukuran relatif terhadap glyph**, bukan jumlah titik.
   Huruf yang memang punya stroke badan kecil (tanda dalam ك, kait ي) tetap dikenali
   sebagai badan lewat `minBodyStrokes`.
2. **Mirror matching lewat `scorePath`.** → Dihapus.
3. **Baru 14 dari 28 huruf.** → Lengkap 28 huruf + hamzah, masing-masing dengan catatan
   pengajaran singkat dalam bahasa Indonesia.
4. **ب ت ث ن memakai badan yang identik.** → Nun sekarang punya mangkuk yang lebih dalam
   (`BOWL_DEEP`), sesuai bentuk sebenarnya.

Ditambah dua hal baru:

- **Titik itu identitas huruf.** Jumlah titik dan sisi (atas/bawah) sekarang **wajib tepat**
  untuk diterima. Dulu selisih satu titik masih lolos — artinya ب bisa diterima sebagai ت.
- **Cek arah kanan-ke-kiri.** Dinilai, bukan ditolak: anak yang membuat bentuk benar tapi
  arah terbalik tetap diberi nilai, dengan pesan "Benar. Lain kali tulis dari kanan ke kiri ya."

Ada juga **pemeriksaan diskriminatif**: tulisan tidak diterima kalau ada huruf *lain* yang
cocoknya jauh lebih baik. Tanpa ini, alif mendapat skor 83% terhadap dal — garis pendek dan
lengkung pendek memang berdekatan di ruang ternormalisasi.

Hasil terukur: **29/29 huruf diterima untuk dirinya sendiri, 0 false accept** dari 812
kombinasi silang.

## 6. Playability — anak 5 tahun dan main berdua

### 6.1 Preflight: dari 7 gerbang jadi 1 langkah

Dulu harus lolos: kamera → model → tangan → tubuh → cubit dikonfirmasi → telapak terbuka
dikonfirmasi → jempol ditahan 900 ms. Dan untuk game tangan 2 pemain, sistem menuntut
**2 tubuh utuh + 4 tangan** terdeteksi di 960×540 — itu tuntutan studio, bukan ruang keluarga.

Sekarang:

- Satu status besar yang menjelaskan apa yang perlu dilakukan sekarang, dalam kalimat biasa
  ("Angkat tangan supaya terlihat kamera", "Maju sedikit ke arah kamera")
- Deteksi pose **tidak lagi wajib** untuk game tangan; pemisahan pemain jatuh ke posisi
  horizontal dan slot wajah
- Gerakan mulai: telapak terbuka ditahan 700 ms (bukan jempol 900 ms)
- Checklist teknis lengkap + diagnostik FPS pindah ke balik tombol **"Mode orang tua"**

### 6.2 Mode Santai jadi default

Kamu memilih "latihan bebas tanpa timer" **dan** "biarkan orang tua memilih" — keduanya
diimplementasikan. Preflight punya pilihan **Santai / Tantangan**, dan **Santai adalah
default**.

- **Santai**: tanpa hitung mundur sama sekali (jam menampilkan ∞), tanpa pengurangan nilai
- **Tantangan**: hitung mundur 90 detik + bonus kecepatan

Timer juga **berhenti otomatis saat pemain hilang dari frame**, dengan grace 2 detik supaya
satu frame yang meleset tidak menghentikan permainan. Dulu jamnya terus jalan sementara
anak pergi ambil minum.

### 6.3 Level per pemain

Ini masalah terbesar untuk main berdua. Dulu `DigitRace` punya **satu** state `level` dan
**satu** soal untuk kedua pemain — anak 5 tahun dan ayah 36 tahun mengerjakan soal yang
sama persis.

Sekarang setiap pemain punya soal sendiri, level sendiri, dan tombol level sendiri.
Default: **Pemain A = TK, Pemain B = SD 2.**

### 6.4 Papan pemain B tidak lagi terhapus

```ts
lockedRef.current = true;
setTimeout(() => { setDigits({ A: "", B: "" }); ... }, 850);
```

Saat A benar, seluruh papan terkunci dan buffer **kedua** pemain dikosongkan. Kerja B yang
sedang setengah jalan hilang. Sekarang hanya papan pemain yang menjawab yang berganti.

### 6.5 Penalti dihapus, bintang masuk

Salah digit dulu berarti **−5 poin**. Salah bentuk itu wujud dari proses belajar menulis,
dan menghukumnya mengajari anak untuk berhenti mencoba. Sekarang: tanpa penalti, ada baris
bintang yang terisi.

### 6.6 Suara

`src/lib/audio/feedback.ts` (baru) — nada benar/salah/mulai/rayakan lewat Web Audio, plus
TTS bahasa Indonesia. Anak 5 tahun belum bisa membaca toast berbahasa Indonesia, jadi umpan
balik tekstual saja praktis berarti tidak ada umpan balik.

### 6.7 Soal tidak lagi identik tiap sesi

```ts
const [random] = useState(() => createRandom(seedFor(kind)));  // seed tetap 0x51aa
```

Seed di-hardcode, jadi urutan soal identik setiap sesi. Sekarang di-seed acak per sesi.

### 6.8 Tombol bisa dijangkau tanpa mouse

Tombol level, pemilih huruf, jeda, kirim, hapus, dan tombol layar akhir ronde sekarang
punya `data-air-target` sehingga bisa dipilih dengan kursor udara. Premisnya *touchless*,
tapi dulu anak tidak bisa mengganti apa pun tanpa mouse.

## 10. "Maximum update depth exceeded" — akar masalah arsitektur

Ini bukan bug kecil. Snapshot kamera didorong ke React state **25 kali per
detik**, lalu setiap konsumen memasang `useEffect` yang bergantung pada objek
snapshot itu — objek yang identitasnya berganti setiap frame. Jadi:

```
frame baru → setSnapshot → render → effect jalan lagi → setState → render → …
```

`MotionPad` memanggil `setCameraCursor` di dalam effect yang bergantung pada
`hand`; `AirCursor` melakukan hal yang sama; `usePresence` dan timer ikut
menambah. Dengan seluruh pohon game ikut render 25×/detik, React akhirnya
memutus rantai itu dengan "Maximum update depth exceeded".

**Perbaikannya: aliran frame keluar dari React state sepenuhnya.**

`useVisionRuntime` sekarang menyimpan frame di `ref` dan menawarkan dua cara
membacanya:

| Cara | Untuk apa | Biaya render |
|---|---|---|
| `subscribe(fn)` | menggambar kanvas, logika pena | **nol** — tidak menyentuh state |
| `getSnapshot()` | pembacaan sesaat di dalam rAF | nol |
| `summary` | jumlah tangan/tubuh/wajah, FPS, jarak | maksimal ~3×/detik, hanya kalau nilainya berubah |

Ditambah dua hook di `useVisionSelector.ts`:

- `useVisionValue(vision, selector)` — render **hanya** saat nilai terpilih
  berubah. Untuk game tubuh yang cuma butuh `body.action` (sebuah string),
  ini mengubah 25 render/detik jadi beberapa render per menit.
- `useVisionFrame(vision, cb)` — callback per frame tanpa state sama sekali.

Yang ikut ditulis ulang: `VisionOverlay` (punya rAF sendiri), `MotionPad`,
`AirCursor`, `PreflightPanel`, dan semua game.

## 16. Skeleton: kenapa garisnya putus-putus

Kamu benar, dan penyebabnya satu baris kode:

```ts
function visible(point, threshold = 0.35) {
  if (typeof point.visibility !== "number") return true;
  return point.visibility >= threshold;   // ← ini
}
```

## 23. "Susah nulis 4 dan 7" — akar masalahnya bukan di pengenalan bentuknya

Pertanyaanmu: kenapa spesifik 4 dan 7 yang susah, bukan angka lain?

Itu petunjuk pentingnya. Kalau masalahnya di algoritma pengenalan bentuk
($P point-cloud + `featurePenalty`), semua angka harusnya kena rata — tapi
tidak. Angka **pendek dan lebar** (0, 2, 3, 5, 6, 8, 9) baik-baik saja; yang
**tinggi dan kurus** (1, 4, 7) yang bermasalah. Itu bukan pola kebetulan bentuk,
itu pola *kotak referensi tangan*.

### Akar masalah: kotak tulis dikunci sebelum tahu seberapa besar yang mau ditulis

`PenMapper` (di `src/lib/interaction/pen-mapper.ts`) memetakan posisi tangan
mentah ke kanvas dengan kotak referensi yang beradaptasi — supaya bekerja untuk
lengan pendek atau panjang, ruangan sempit atau luas. Supaya bentuk tidak
berubah di tengah tulisan, kotak itu **dikunci** persis saat cubitan dimulai
(`lock()`), dan baru dibuka lagi setelah selesai.

Masalahnya: kotak yang dikunci itu adalah kotak dari **sebelum** tulisan ini
dimulai — dari sekadar tangan menggantung/berpikir sebentar. Kotak defaultnya
sendiri lebih **lebar daripada tinggi** (0,30 lebar x 0,26 tinggi), dan kalau
tangan diam sejenak sebelum menulis, kotak itu menyusut pelan-pelan mendekati
ukuran default itu. Begitu tulisan dimulai dan kotak dikunci sekecil itu,
gerakan tangan yang sebenarnya jauh lebih tinggi dari kotaknya **terpotong**
(clipped) di tepi atas/bawah — bukan diskalakan, betul-betul rata, seperti
digaris lurus di ujungnya.

Angka 0, 3, 5, 8, 9 hampir sama lebar dan tinggi, jadi kebetulan pas dengan
kotak default yang lebar. Angka 1, 4, 7 secara alami jauh lebih tinggi daripada
lebar — persis yang paling parah kepotong. Saya buat simulasi memakai bentuk
templat asli lewat `PenMapper` yang sama seperti aplikasi nyata, dan hasilnya
jelas:

| Kondisi | Sebelum perbaikan | Sesudah perbaikan |
|---|---|---|
| "7" ditulis setelah tangan diam sebentar | terbaca **9**, keyakinan 0.60 | terbaca **7**, keyakinan 0.68–0.83 |
| "4" ditulis setelah tangan diam sebentar | terbaca 4 tapi nyaris seri dengan "6" (jarak 0,056 vs 0,057) | terbaca **4** jelas, keyakinan 0.86–0.97 |
| "0" (kontrol, sudah lebar) | tidak terpengaruh | tidak berubah |

Perbaikannya di `PenMapper.lock()`: begitu kotak dikunci, kotak itu dilebarkan
dulu ke ukuran minimum yang cukup luas untuk satu karakter penuh (mengambil
titik tengah kotak lama, bukan menggeser posisinya) — kalau kotaknya sudah
lebih besar dari itu (karena pemain memang menjangkau jauh), dibiarkan saja.
Ini hanya menambah ruang, tidak pernah mengurangi. Default kotak sebelum
menulis pun saya ubah supaya lebih tinggi daripada lebar, karena tulisan tangan
rata-rata memang begitu — bukan sebaliknya.

### Perbaikan pendukung: deteksi "loop" sekarang mensyaratkan lengkungan asli

Selagi menyelidiki, saya temukan satu sumber gangguan lagi: fitur pemisah 6 vs
9 (di mana loop-nya berada) memakai heuristik "jalur balik dekat dirinya
sendiri = loop". Itu cocok untuk 6/9/8/0, tapi 4 dan 7 yang ditulis tanpa
mengangkat tangan (garis diagonal 4 yang memotong palangnya, atau palang 7
yang digambar dengan gerakan mundur alih-alih diangkat) juga bisa memicu
"loop" palsu di titik potongnya — padahal itu cuma sudut tajam, bukan
lengkungan.

`analyzeLoops` (`src/lib/engine/features.ts`) sekarang menghitung total
putaran terarah (*signed rotation*) di sepanjang rentang yang dicurigai.
Lengkungan asli berputar konsisten satu arah dan totalnya besar; sudut tajam
atau tangan yang goyang lalu balik arah saling meniadakan dan totalnya kecil.
Ambangnya: minimal ±3 radian (~172°) putaran konsisten sebelum dianggap loop
sungguhan. Karena aturan ini membuat deteksi loop lebih ketat, aturan "6/9
tanpa loop sama sekali" di `featurePenalty` juga dipertegas (dari penalti 0,22
jadi 0,5) — tulisan tangan asli nyaris tidak pernah menghasilkan 6 atau 9 yang
benar-benar tanpa lengkungan sedikit pun, jadi itu bukti kuat, bukan sekadar
petunjuk lemah.

## 26. "Buka telapak kadang ga bisa"

Ini bug yang bagus untuk ditemukan, karena penyebabnya persis kebalikan dari
yang terlihat. Kode lamanya:

```ts
if (gesture === "open") started ??= now;
else started = null;        // satu frame meleset -> hitungan mulai dari nol
```

Klasifikasi tangan tidak stabil frame per frame — satu jari turun sedikit di
bawah ambang lurus, tangan berputar, tracker drop satu frame. Selama menahan
500 ms di ~25 fps, meleset satu frame itu **wajar, bukan langka**. Dan setiap
kali meleset, hitungannya diam-diam direset ke nol. Makanya kadang jalan,
kadang tidak, tanpa pola yang kelihatan.

Sekarang ada `GestureHold` (`src/lib/vision/gesture.ts`): kedipan harus
**bertahan** lebih dari 220 ms sebelum tahanan dianggap batal. Jadi yang
diukur adalah berapa lama kamu benar-benar menahan gestur, bukan berapa
beruntung classifier-nya. Ada juga cooldown supaya satu tahanan panjang tidak
memicu berkali-kali.

Sekalian: ambang "telapak terbuka" diturunkan dari 4 jari lurus jadi 3. Jari
manis anak kecil jarang benar-benar lurus sampai ambang 155°, jadi tangan
yang jelas-jelas terbuka sering tidak terhitung "open".

## 28. Angka 4: ternyata bukan soal bentuk sama sekali

Saya uji ulang delapan variasi "4" yang realistis lewat pipeline yang sama

| Cara menulis 4 | Terbaca |

| 4 dua goresan standar | **4** (1,00) |
| 4 goresan tegak dulu, baru V | **4** (1,00) |

ditulis. Perangkap yang sama mengintai 5 dua goresan dan 7 berpalang.

sementara — kartu bacaan baru muncul setelah 900 ms (bukan 420 ms) dan baru
mengunci sendiri setelah 2400 ms lagi. Totalnya lebih dari 3 detik untuk
mengangkat tangan, mengarahkan, dan menarik goresan kedua. Begitu goresan
kedua ada, karakternya kemungkinan besar selesai dan waktu cepatnya kembali.

## 33. "Pakai object detection kayak YOLO biar skeleton-nya ga kabur ke orang lain"

Permintaan awalnya: pakai [Ultralytics YOLO](https://github.com/ultralytics/ultralytics)
di dalam engine supaya skeleton dan face mesh "mengunci" ke pemain dan tidak
loncat ke orang lain, terutama saat main berdua.

**Soal lisensinya dulu, karena ini yang menentukan arah:** Ultralytics YOLO
itu dual-license. Versi gratisnya AGPL-3.0 — copyleft, artinya kalau dipakai
di produk ini, seluruh source code project (bukan cuma bagian yang menyentuh
YOLO-nya) wajib dirilis terbuka. Untuk tetap closed-source dan komersial,
wajib beli Enterprise License mereka (harga custom, tidak dipublikasikan).
Jadi "gratis dan boleh komersial" itu tidak akurat kalau produknya mau tetap
tertutup — itu justru kasus yang paling jelas butuh Enterprise License.

Di luar soal lisensi, YOLO juga bukan alat yang pas untuk masalah ini secara
teknis. Ultralytics itu Python-first — untuk jalan real-time di browser perlu
diekspor dulu ke ONNX/TensorFlow.js, pekerjaan besar tersendiri. Dan yang
lebih penting: MediaPipe yang sudah dipakai di app ini **sudah** mendeteksi
banyak orang sekaligus (`PoseLandmarker`/`FaceLandmarker`/`HandLandmarker`
multi-pose). Menambah YOLO di atasnya tidak menambah kemampuan deteksi -
masalah "skeleton loncat ke orang lain" bukan soal kurang mendeteksi, tapi
soal engine gagal **mengunci identitas antar frame**.

Akar masalahnya, ditemukan dengan membaca `BodySlotTracker` di
`src/lib/vision/player-assignment.ts`: tracker itu memang sudah menjaga slot
A/B secara temporal, tapi setiap frame dia **selalu** memaksa observasi yang
ada (maksimal `numPoses`/`numFaces` = jumlah pemain) ke slot A/B mana pun
yang jaraknya paling dekat - tanpa pernah menolak kandidat yang jaraknya
tidak masuk akal. Begitu satu pemain sempat tidak terdeteksi satu frame saja
(nunduk, kepotong badan lain, dsb), slot itu langsung "diserahkan" ke siapa
pun yang paling dekat saat itu - orang asing sekalipun. `assignHandToPlayer`
punya kelemahan yang sama di sisi tangan: sejak perbaikan dead-band minggu
lalu, tangan yang terdeteksi **selalu** dipaksa masuk ke pemain A atau B
tanpa batas jarak, jadi tangan orang lain yang lewat pun ikut tertarik.

**Perbaikan (murni di dalam engine yang sudah ada, tanpa model baru, tanpa
isu lisensi):**

* `BodySlotTracker` dan `FaceSlotTracker` sekarang punya "jump budget" -
  jarak maksimum yang masuk akal untuk pemain bergerak dalam satu frame.
  Kandidat yang lebih jauh dari itu ditolak, bukan diterima begitu saja
  karena dia yang "paling dekat". Budget ini melebar sedikit demi sedikit
  selama pemain hilang (supaya yang benar-benar kembali tetap dikenali),
  dengan batas atas.
* Ternyata cara lama memasangkan 2 observasi ke slot A/B (pilih total jarak
  terkecil dari dua opsi) punya bug tersembunyi: kalau salah satu observasi
  itu orang asing, pasangan yang "totalnya termurah" bisa memaksa
  kecocokan yang bagus (misal pemain A) ikut ditolak juga. Diganti dengan
  setiap slot mengklaim sendiri kandidat terdekatnya, independen.
* Lapisan tambahan: kalau kandidat hanya masuk lewat budget yang sudah
  melebar (bukan budget dasar), dia harus muncul di posisi yang **sama**
  dua frame berturut-turut baru dipercaya. Ini yang mencegah orang lewat
  yang kebetulan menyeberang tepat di bekas posisi pemain yang sempat
  hilang ikut "tertangkap".
* `isHandPlausible()` (baru) menolak tangan yang jaraknya jauh dari kedua
  pemain yang sedang terlacak, sebelum `assignHandToPlayer` sempat memaksa
  tangan itu ke pemain A/B. Tetap tidak mengembalikan "bukan siapa-siapa"
  untuk tangan pemain sungguhan (itu yang memperbaiki bug dead-band minggu
  lalu) - ini cuma menyaring tangan yang jelas bukan milik siapa pun yang
  sedang dilacak.

**Bagian yang terlihat, sesuai permintaan:** setiap badan yang terlacak
sekarang digambar dengan kotak putus-putus tipis (bukan panel penuh - itu
kesalahan yang sama yang baru diperbaiki di game pilih-jawaban) plus label
kecil "PEMAIN A"/"PEMAIN B" di atasnya, warna sesuai pemain. Kalau kotak itu
diam menempel di satu orang, kuncinya sedang bekerja; kalau meloncat, itu
tanda untuk dilaporkan lagi.

Diverifikasi dengan simulasi headless (bukan kamera sungguhan) atas
`BodySlotTracker`/`FaceSlotTracker`/`isHandPlausible` langsung, karena
mensimulasikan kamera + MediaPipe yang sungguhan di luar jangkauan alat di
sesi ini:

```
300 frame, 15% di antaranya MediaPipe "salah lihat" orang asing di posisi
acak menggantikan Pemain B: 0 pengambilalihan slot (sebelumnya perbaikan
tambahan ini, masih ada 1 dari 60 frame yang lolos - makanya lapisan
konfirmasi dua-frame di atas ditambahkan)

Pemain yang genuinely kembali ke posisi lamanya setelah absen singkat:
tetap dikenali sebagai pemain yang sama.
```

45 test engine baru/diperbarui (dari 38) mengunci semua perilaku di atas,
plus kontrak baru di `audit-source.mjs` supaya build gagal kalau gerbang
plausibilitas ini dilepas lagi.

```

                  vision/engine terkait + sisanya, 5 simulasi, build 19 halaman)
```

**Yang masih perlu tangan sungguhan:** kotak kunci + label ini belum saya
lihat langsung di kamera sungguhan (sesi ini tidak punya kamera untuk
dites) - tolong konfirmasi di HP/laptop kalian apakah kotaknya menempel
stabil ke masing-masing pemain, dan apakah masih ada momen "loncat" yang

## 34. Dodge jadi Beat Motion, papan skor, dan homepage baru

Enam permintaan sekaligus di putaran ini. Yang paling menarik justru yang
tidak diminta secara eksplisit: kenapa "cursor skeleton"-nya terasa mati.

### Dodge → Beat Motion (menghindar jadi mengenai)

Tujuannya dibalik: bukan menghindari objek, tapi **mengenai** panah yang
turun, seperti Pump It Up. Ini bukan sekadar ganti aturan — game menghindar
justru memberi nilai pada anak yang **paling sedikit bergerak**, dan itu
pelajaran yang aneh untuk permainan yang tujuannya membuat anak lima tahun
bangun dari sofa. Menangkap membalik insentifnya: satu-satunya cara dapat
skor adalah benar-benar pindah ke tempat panahnya, berulang kali, makin cepat.

* **Tiga lajur saja** (kiri / tengah / kanan). Lompat dan jongkok dihapus:
  keduanya butuh baseline tubuh terkalibrasi untuk terdeteksi sama sekali,
  telat memicu saat memicu, dan lompatan kecil di ruang tamu kecil sering
  tidak terbaca sama sekali.
* **Panah besar**, digambar sebagai SVG, bukan teks di dalam kotak. Versi
  lama menaruh kata "LOW"/"HIGH" di kotak kecil — pemain yang berdiri dua
  meter dari layar memang tidak akan sempat membacanya.
* **Lebih banyak objek**: cadence mulai 950 ms dan mengetat sampai 520 ms
  seiring ronde berjalan, jadi makin lama makin padat.
* **Combo & akurasi**: 4 tangkapan beruntun menaikkan pengali (maks x5).
  Ada toleransi timing 260 ms — meminta ketepatan per-frame ke anak lima
  tahun membuat game terasa rusak, bukan terasa sulit.
* **Durasi 1 / 3 / 5 menit + custom** (1–30 menit), tombolnya di bawah
  panggung. Game ini selalu bertimer walau sesi diset santai: ronde ritme
  harus punya akhir supaya skornya berarti.

### Kenapa penanda posisinya tidak responsif

Akar masalahnya bukan rendering, tapi sumber datanya. Versi lama membaca
`classifyBodyAction`, yang baru melaporkan salah satu dari tiga keadaan
**setelah** pemain bergeser lebih dari 12% lebar frame dari baseline yang
diambil dari 24 frame pertama. Dua akibatnya: langkah yang terasa besar di
ruang tamu sering tidak melewati ambang itu sama sekali, dan begitu lewat,
penandanya *teleport* di antara tiga titik tetap.

Sekarang posisinya dibaca langsung dari `body.center.x` yang sudah dihaluskan,
lewat `useVisionFrame`, lalu ditulis langsung ke DOM — tanpa React state per
frame, tanpa kalibrasi, tanpa ambang. Band 0.24–0.76 direntangkan ke lebar
penuh (pemain yang utuh di frame memang tidak pernah menyentuh tepi), dan
pemilihan lajur pakai histeresis: keluar dari lajur butuh gerakan lebih besar
daripada masuk, supaya berdiri di perbatasan tidak membuat lajur berkedip
beberapa kali per detik — kedipan itulah yang dirasakan sebagai "tidak
responsif", karena game tidak pernah diam cukup lama untuk ditindaklanjuti.

Diverifikasi headless: 200 frame jitter di sekitar perbatasan menghasilkan
**maksimum 1** perubahan lajur.

### Panel biru dihapus

`.dodge-field` punya `background: linear-gradient(rgba(54,96,154,.32) ...)`
yang menutupi seluruh area kamera — persis di atas muka dan badan pemain.
Sekarang transparan; lajur ditandai garis putus-putus saja. Vignette
`.camera-stage::after` juga dipersempit ke strip atas-bawah saja (tempat HUD
dan toast), dan `brightness(.86)` pada video dicabut — meredupkan kamera untuk
menonjolkan UI putih itu menyelesaikan masalah yang salah. Semua sensor
(skeleton, face mesh, kotak PEMAIN A) tetap tampil. Ada kontrak `audit-source`
baru yang membuat build **gagal** kalau tint itu dipasang lagi.

### Papan skor

Lokal dulu (localStorage), tapi dibentuk seperti papan server: `submitScore`
menulis lokal lalu memanggil `pushRemote` yang sengaja masih kosong, meniru
pola `useProgressSync` yang sudah ada. Menjadikannya online nanti = mengisi
satu fungsi itu, bukan menyentuh sepuluh game.

* Di akhir **setiap** game muncul peringkat + kotak nama. Peringkatnya
  dihitung dan ditampilkan **sebelum** apa pun disimpan — anak yang baru
  dapat peringkat 3 harus bisa melihat itu tanpa lebih dulu disuruh mengisi
  formulir.
* Nama terakhir diingat, jadi tidak perlu diketik ulang tiap ronde.
* Halaman `/papan-skor` menampilkan semua game, dan ada ringkasan juara di
  homepage.

Satu bug asli tertangkap test di sini: preview peringkat memakai `>` (skor
yang lebih baik saja), sedangkan urutan simpan memakai tie-break waktu. Jadi
skor yang menyamai pemuncak akan ditampilkan "#1" lalu berubah jadi "#2"
begitu tombol simpan ditekan — angka yang berubah di depan mata anak terbaca
sebagai game yang salah hitung. `rankOf` sekarang memakai `>=`, dan ada test
yang memaksa preview selalu sama dengan peringkat setelah penyisipan.

### Homepage dirombak total

Versi lama adalah *landing page perangkat lunak* — hero abu-biru, filter bar,
kotak pencarian, paragraf tentang privasi, dan SVG dekoratif yang justru
render sebagai gumpalan hitam (itu "grafis error" di laporan). Yang membuka
layar ini biasanya anak lima tahun yang ingin menekan benda paling besar dan
paling berwarna lalu mulai bergerak.

Sekarang: judul besar bergradasi, sepuluh kartu game bergradasi masing-masing
dengan warnanya sendiri (warna jadi penanda arah, bukan teks), papan skor,
empat langkah cara main, dan ilustrasi SVG buatan sendiri (anak di depan
kamera dengan skeleton dan kotak PEMAIN A) yang ikut dalam kode sehingga tidak
mungkin 404. Filter, pencarian, dan sebagian besar teks dibuang.

Satu bug layout tertangkap saat verifikasi: satu tombol `white-space: nowrap`
di dalam grid item (yang defaultnya `min-width: auto`) diam-diam melebarkan
seluruh kolom melewati viewport, sehingga teks hero terpotong di HP. Diperbaiki
dengan `min-width: 0` pada anak grid.

Diverifikasi lewat browser sungguhan (mode mouse, tanpa kamera): satu ronde
Beat Motion 1 menit dimainkan sampai habis, skor 2500, kartu akhir ronde
menampilkan peringkat, nama disimpan, dan entri masuk localStorage dengan
`durationSeconds: 60`. Homepage dan `/papan-skor` dicek di 390×844 dan
1280×900, tanpa error konsol.

**Yang masih perlu tangan sungguhan:** apakah band 0.24–0.76 pas dengan jarak
main kalian yang sebenarnya. Kalau anak harus melangkah terlalu jauh untuk
sampai lajur pinggir, angka itu (`BAND_MIN`/`BAND_MAX` di
`src/lib/engine/lanes.ts`) tinggal dirapatkan; kalau terlalu sensitif,
dilebarkan.
